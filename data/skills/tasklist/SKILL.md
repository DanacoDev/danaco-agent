name: tasklist
description: The task list. The main agent and the consultant list, create, update, and delete tasks. Another subagent can list or add a result. Work that should run now is one in_progress task. Each part of that work is a step on that task.
version: 1.0.0

args action. The main agent uses list, create, update, delete, or stop. The consultant uses list, create, update, or delete. Another subagent uses list or result.

list: no other args.
create: one scheduled task, or tasks for work that should run now. A scheduled task uses title, steps, agent, status, schedule_time (YYYY-MM-DD HH:MM), recurrence (none, 5min, 15min, 30min, hourly, daily, weekly, or monthly). Do not save a date in the title. steps is required. Do not put the instructions in a paragraph on the task. Each step is an object with title, agent, and description. description is required. It names the files, lists, and skills to use, and what to save or return. A title alone is rejected and the task is not added. A create with no steps is rejected and the task is not added. none means run once. Leave schedule_time empty only when the work should run as soon as allowed and nobody named a time. The tool stores a time 2 minutes ahead so you can correct a mistake before the task runs. The reply shows that time. After you insert or update a task, list the tasks and review every one. Check that the titles, steps, agents, and times match what was intended. If something is wrong, update that task. Do not delete it to start sooner, and do not delegate. The scheduler starts it. Do not invent a clock time for that case. When the user names a time, pass that clock time. At 9:15 every Monday is schedule_time for the next Monday at 09:15 and recurrence weekly. Do not leave that time empty, and do not move it by 2 minutes. A missed Monday is not sent late. The next Monday 09:15 is the next run. Set schedule_time to never to inactivate a task and keep it. That task stays on the list and does not run. For work that should run now, pass tasks. tasks is a list. Each item has title, agent, and steps. A step is an object with title, agent, and description. agent on a step can be human. Use human when that step is a review or an approval for the user, such as checking which rows to keep or approving a result. Do not delegate a human step. Show the user the file and wait. Cross that step off only after they say they read it and it is OK. A scheduled run cannot cross it off. The task itself stays assigned to the subagent who does the work. Do not assign the whole task to human. A plain string is rejected. Pass an object with title, agent, and description. A piece the user will read is one writer task, not one step that repeats the title. Its steps are objects: Write the piece and save it as markdown in wiki/. Create the PDF in docs/ when a PDF was asked. Read the PDF and check it. Report the file path. Each description names the file. Check the task list first. An exact duplicate is the same title, the same step, the same agent, run once, and either no schedule or a start within 2 minutes. It is not added. The result names that task. Use that task. Before create, list the tasks and check for a duplicate or a similar task. Do not add a task for work that is already there. After create or update, list the tasks and review every one. Read the new id. Check that the titles, steps, agents, and times match what was intended. If something is wrong, update that task. If the list says scheduled, do not delegate. The scheduler starts it when that time arrives. If the new title is not in the list, it was not created. Do not delegate, and do not say that you created it.
update: id, plus any of status, steps, result, agent, schedule_time, recurrence, replace_steps. To change a task, call update with its id. Do not delete it and create a new one. Passing steps adds a step, or updates the step that is already there. A new description, a clearer title, or a different agent is written onto that step. A step still needs a description. To replace the open steps, pass replace_steps true and the full new list. Done steps stay. The schedule stays unless you pass schedule_time. To cross off a step, pass that step with result set to done, or to one line of what it produced. That marks the step done. Do not pass replace_steps to mark a step done. A task marked held was stopped by the user. Leave it held unless the user asked you to change, resume, or end it. A new schedule or repeat resumes it. Set schedule_time to never to inactivate a task and keep it. It stays in_progress and does not run. A real time turns it back on. An empty time runs in 2 minutes. Set result to one line of the outcome or the current progress, such as: Wrote 100 rows to database file.db. Do not paste your reasoning, the task list, or tool output. Do not set done. If the finished step is still open, pass that step with result set to the same line. A run-once task becomes done when every step is crossed off.
delete: id. Removes that task. Use it only when the user names that task and asks you to remove it. Do not delete a task because its steps are wrong, the plan changed, or its start is a couple of minutes ahead. Those minutes are so you can correct a mistake. Update that task instead. Deleting a task does not stop a job that already started.
stop: no other args. The main agent uses this. It stops a task or subagent job that is already running. The list names a job that is still running, deleting a task does not stop that job, and when the user says to stop the work the main agent calls tasklist action stop before saying the board is clear.
result: id and result. result is one line, the outcome or the current progress, such as: Wrote docs/story.pdf. A subagent adds that line to the task it was given. That crosses off the current step when it is the one just finished. A later step stays open while an earlier step is open. Do not say the task is complete then. Do not pass done.

A task is in_progress or done. The list shows [scheduled] and scheduled for the clock time when that time is still in the future. That task is waiting. Its open steps also say scheduled. Do not start them and do not add a result. scheduled is not a status you set. The stored status stays in_progress. When the time has arrived, the list says [in_progress]. in_progress means the step is still open, a task whose time has arrived, a repeat with no future time, or a task set to never. It does not mean a subagent is running. The name in parentheses is who should do that step. A subagent is running only when the list says that agent is working. If it does not, nobody is. Delegate the open step. Do not wait. A repeating task stays in_progress. done = every step on a run-once task is crossed off. You do not set it. result is one line of the outcome or the current progress. There is no backlog. Never (inactivated) is how you disable a task and keep it. An idea for later is not a task. Write it in the project wiki. The main agent and the consultant create, update, and delete tasks. Another subagent can only add a result. The main agent checks that result, then updates the task. After the consultant changes the list, the main agent delegates the first open step unless that task is scheduled. You cannot archive a task, and you cannot set a repeating task to done.

Tasks are for an agent, or a reminder that will send something or take an action. Not a static todo for the user.
After the user has chosen now or scheduled, every future event needs its own task. Work that should run now is one task. Each part of that work is a step on that task. An open step stays on its task. Update that task. Do not create a new task from a step. A scheduled task is create with title, steps, and schedule_time. Saying you will do it later does not schedule it. Split several events into separate tasks. When the work repeats, set recurrence and have the coder register a skill with write_skill for the repeated steps when that is possible. Name that skill in the step description. A file in the project is not a skill.
A result is assigned to the subagent who produces it. Planning with the user is assigned to orchestrator.
Do not add a task while you are still planning. Set a task to in_progress when the user chose now and you start it, or when a scheduled task is due. Do not set a task to done. A run-once task becomes done when every step is crossed off. Leave a repeating task in in_progress, with its repeat still set. Do not delegate a new task in the planning turn. A small contained request is still created in that turn. It is not delegated in that turn.
After every delegated job, list the tasks and update the matching ones before you reply or delegate again, even when this chat does not mention any tasks. A cleared context still has tasks. Do not archive. Do not explain these steps in place of updating them.
